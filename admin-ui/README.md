# BantayAralan -- Admin UI (prototype)

A working, click-through prototype of the BantayAralan admin interface:
Dashboard, Events & Logs, Event Detail (video + screenshot evidence), Head
Count, Insights & Statistics, and a Detection Enable/Disable control, built
as a small Python (Flask) backend serving a plain HTML/CSS/JS frontend. It
replaced an earlier Figma-based design pass after the Figma team's
Starter-plan MCP quota was exhausted mid-session (see git history /
conversation for context) -- the visual design carried over 1:1 from the
tokens and components validated in Figma.

**This is the sole and primary BantayAralan admin UI.** A separate native
desktop prototype (`desktop-app/`, PySide6) existed briefly and was removed
once the finalized prototype paper settled the project direction as
web-only -- see `../Knowledge/11 - Decisions/Web Application as Sole Admin UI.md`.

**This is a UI/UX prototype with mock data, not the real BantayAralan
system.** There is no camera, no YOLO/ByteTrack detection pipeline, and no
real video capture behind it -- see "What's real vs. mocked" below and the
project root [`CLAUDE.md`](../CLAUDE.md).

## Running it

Two run modes, same backend, same frontend -- both are the same web
application, just shown differently:

**Web app** (just a browser tab):
```bash
pip install -r requirements.txt
python run_web.py
```
Opens `http://127.0.0.1:5057/` in your default browser.

**Desktop window** (native window via [pywebview](https://pywebview.flowrl.com/)):
```bash
pip install -r requirements.txt pywebview
python run_desktop.py
```
This opens a real OS window wrapping the exact same app. It was syntax-checked
and its dependency installed during development, but the window itself
wasn't launched from the automated build session (opening a GUI window from
a non-interactive tool call risks hanging with no way to close it) -- run it
yourself and confirm it opens correctly on your machine.

Mock data is seeded automatically into `data/bantayaralan.db` (SQLite) on
first run. Delete that file to reset/reseed.

## Packaging as a standalone .exe

Not built in this session -- documented here for when you want it:

```bash
pip install pyinstaller
pyinstaller --name BantayAralan --onefile --add-data "frontend;frontend" run_desktop.py
```
The `--add-data "frontend;frontend"` flag is required so the bundled exe can
still find the HTML/CSS/JS at runtime (PyInstaller's Windows syntax uses
`;` as the separator; use `:` on macOS/Linux). Test the resulting
`dist/BantayAralan.exe` on a clean machine before distributing it.

## What's real vs. mocked

| Piece | Status |
|---|---|
| Dashboard, Events/Logs, Event Detail screens, filters, search, sort | Real, working code |
| Loading / empty / no-results / error / evidence-unavailable states | Real, working code |
| Event data (42 seeded mock events, all 4 categories) | Synthetic, generated by `backend/seed.py` -- not from a real detector |
| Snapshot evidence | A generated placeholder SVG (`/api/events/<id>/snapshot.svg`), not a real camera frame |
| Video evidence | **Fully simulated in the browser** -- the player UI (play/pause, scrub, time, volume, fullscreen buttons) is real and interactive, but there is no actual video file or codec involved. See "Video evidence backend requirements" below. |
| Head Count | Real working form + `head_counts` table -- recording is manual (no camera pipeline yet); ~10 sessions are seeded as synthetic history |
| Detection Enable/Disable toggle | Real, persisted (`detection_state` table) -- gates event generation only; camera/monitoring status shown separately are still hardcoded-true mock values |
| Statistics / Classroom Insights / Suggestions | Real SQL aggregation + simple rule-based thresholds over the seeded mock event data -- not a validated statistical or behavioral model (see `admin-ui/CLAUDE.md`) |
| System status panel (camera/monitoring) | Hardcoded-true mock values from `/api/status` |
| Authentication | None -- intentionally out of scope per the design brief (admin-only, single deployment, no user management) |

## Video evidence -- backend requirements (not yet implemented anywhere)

The proposal's working draft does not yet describe event-video capture in
detail, and this codebase does not implement it. For the Event Detail
video player to show *real* footage instead of a simulated timeline, the
detection system would need to:

1. Keep a rolling buffer of recent frames per camera (to capture the period
   *before* an event is detected, not just after).
2. On a detected event, cut a clip spanning a defined window around the
   trigger (e.g. -10s/+10s) instead of just a snapshot.
3. Encode and store that clip (with a retention/storage strategy -- see the
   open decision on retention in the root CLAUDE.md).
4. Associate the clip with the event row (a `video_path`/`video_url` column
   next to the existing `snapshot_available` column in `backend/db.py`).
5. Serve it as a byte-range-capable static file or stream so the browser
   `<video>` element (or an equivalent) can seek/scrub it -- this frontend's
   simulated player is structured so swapping in a real `<video>` element
   later is a small, contained change (`renderVideoTab` in
   `frontend/js/views/eventDetail.js`).

## Privacy

No student names, IDs, or facial-recognition output appear anywhere in this
UI, seeded data, or generated placeholder imagery -- see
`.claude/rules/privacy-and-ethics.md` at the repo root.
