# Event Model

An **event** is a single logged occurrence of disruptive behavior or classroom disorder. (Use "event," not "offense" — the codebase and design brief consistently use "event.")

## Current implementation (Implemented, mock data)
`admin-ui/backend/db.py` defines the `events` table (a separate
`desktop-app/app/data.py` copy existed through 2026-09-23 and was removed —
see [[Web Application as Sole Admin UI]]):

```sql
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    category TEXT NOT NULL CHECK (category IN ('standing', 'trash', 'misaligned', 'other')),
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    occurred_at TEXT NOT NULL,          -- ISO 8601 timestamp
    video_available INTEGER NOT NULL DEFAULT 0,
    snapshot_available INTEGER NOT NULL DEFAULT 0,
    evidence_note TEXT,                 -- shown when evidence is unavailable
    status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'resolved'))
);
```

- **Four categories**: `standing`, `trash` ("Trash / Scattered Objects"), `misaligned` ("Misaligned Seat"/Table), and a catch-all `other`. Note: the proposal's narrative only explicitly names three (standing behavior, trash detection, misaligned furniture) — `other` is an implementation addition, not stated in the proposal. **Changed from proposal** (additively — not a conflict, just an extra catch-all).
- Most rows are still synthetic, generated by a fixed-seed random generator (`seed()` in `admin-ui/backend/seed.py`) — ~42 events spread across the last 7 days. Seeded rows are always `status='resolved'`. As of 2026-09-26, real `trash`-category rows can also come from `detection/monitor_trash.py` (see [[Trash Monitoring Integration]]) — these are inserted `status='active'` and later flipped to `'resolved'` when the tracked item stops being detected.
- No student names, IDs, or identifying content in any field.

## Working direction (per current project guidance)
- **Events have a two-value status field** (`active`/`resolved` only — not a richer New/Reviewed/Resolved workflow) — see [[Trash Monitoring Integration]], which superseded the earlier [[No Event-Status Field]] decision with explicit user confirmation.
- Both video and screenshot evidence may be associated with one event — see [[Evidence System]].

## Not yet implemented
- Real event creation from detection exists now, but only for `trash`, only via a manually-run one-off script (`detection/monitor_trash.py`), not an always-on service, and not for `misaligned` or `standing`.
- Any linkage between an event and a specific camera/frame/model confidence score **in the database** — `monitor_trash.py` tracks position in its own process memory (not persisted), and puts the confidence value in the free-text `description` rather than a structured column. See [[Trash Monitoring Integration]] for why, and its "Known limitation" (position state is lost if the script restarts).
